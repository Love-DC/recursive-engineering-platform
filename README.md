## Prototype safety boundary

The SQL under `db/prototype` is exercised only against an ephemeral CI database. It is not a Supabase deployment migration, production schema, or production authorization interface. The registration prototype uses a trusted single-Owner test boundary; caller-supplied `project_id` is routing data, not proof of project authorization. The identity key is treated as already normalized by its caller; the database enforces exact equality for the supplied identity version.

The Stage 1B tables model project/resource grants, execution attempts, resource claims, dependency graph membership, OwnerDecision provenance, evidence, and external operation receipts. The Stage 2A/2B prototype protocols are implemented and tested in disposable PostgreSQL CI. Stage 3 delivery and external-operation reconciliation are implemented, independently reviewed, merged, and post-merge verified in PR #49 for the disposable PostgreSQL 17.12 prototype only. T12/T13/T14/T15/T21/T22 passed the Stage 3 protocol suite; exact candidate and merge evidence is recorded above. The connected GitHub session surface still does not provide an independently authenticated native-approval principal, and Deployment is explicitly unsupported. Remaining unimplemented areas include path-overlap resource locking (T06 PARTIAL), authenticated production project authorization, evidence-derived memory (T25), and bounded discovery/decomposition (T19/T20). Stage 4B Context Compiler is implemented as a candidate in PR #70. The first four review rounds' technical findings have been remediated, including cache freshness, bounded Evidence materialization, lock ordering, resource association serialization, complete Evidence byte accounting, dependency batch locking and READ COMMITTED authorization freshness. The old RAE system remains separate and unchanged.
