## Prototype safety boundary

The SQL under `db/prototype` remains a trusted single-Owner prototype, not a production migration or authorization interface. For an isolated, non-production Supabase A0 pilot, use the compatibility bootstrap and ordered install path in [`db/supabase/README.md`](db/supabase/README.md); do not apply the raw prototype chain directly to a hosted Supabase project. The registration prototype uses a trusted single-Owner test boundary; caller-supplied `project_id` is routing data, not proof of project authorization. The identity key is treated as already normalized by its caller; the database enforces exact equality for the supplied identity version.

The Stage 1B tables model project/resource grants, execution attempts, resource claims, dependency graph membership, OwnerDecision provenance, evidence, and external operation receipts. The Stage 2A/2B prototype protocols are implemented and tested in disposable PostgreSQL CI. Stage 3 delivery and external-operation reconciliation are implemented, independently reviewed, merged, and post-merge verified in PR #49 for the disposable PostgreSQL 17.12 prototype only. T12/T13/T14/T15/T21/T22 passed the Stage 3 protocol suite; exact candidate and merge evidence is recorded above. The connected GitHub session surface still does not provide an independently authenticated native-approval principal, and Deployment is explicitly unsupported. Remaining unimplemented areas include path-overlap resource locking (T06 PARTIAL) and authenticated production project authorization. Bounded discovery/decomposition (T19/T20) is now implemented and tested for the disposable prototype. The old RAE system remains separate and unchanged.
