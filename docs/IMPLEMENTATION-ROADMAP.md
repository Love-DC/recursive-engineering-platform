## Architecture-to-implementation stage crosswalk

The stage numbers describe two different planning views and must not be read as a one-to-one renumbering:

| Architecture Snapshot v2.0 | Implementation roadmap | Mapping |
|---|---|---|
| Stage 1 — Work registration and coordination, including the required atomic coordination and authorization guarantees | Stages 1A and 1B | Preparatory implementation slices: canonical Work registration and the minimum coordination data model. These slices do not complete architecture Stage 1. |
| Remaining architecture Stage 1 guarantees | Implementation Stage 2A + Stage 2B | Stage 2A implements transactional claim/resource reservation, lease/takeover/fencing, and claim-time eligibility checks. Stage 2B implements dependency mutation, DAG safety, graph-wide concurrency, and READY invalidation. |

Architecture stage definitions remain unchanged; implementation Stage 2A does not complete the remaining Stage 1 guarantees by itself.

## Stage 4B — authorized Context Compiler (merged and post-merge verified prototype)

The merged Stage 4B implementation adds `0010_stage4b_context_compiler.sql` and `scripts/test_stage4b_context_compiler.py`. PR #70 merged at `feac3eb3b740fbea86f984e4d5dafb85f0d10351` after seven independent review rounds; the seventh round returned PASS on candidate HEAD `65571a1cc6fe8e0f814170ec205ee956dba3d4da` (Issue #77). Exact-merge post-merge [Run #45948690687 — SUCCESS](https://github.com/Love-DC/recursive-engineering-platform/actions/runs/45948690687) passed Repository contract job `140339226637`, PostgreSQL integration job `140339226311`, and the Stage 4B test step. This is merged and post-merge verified for a disposable PostgreSQL 17.12 prototype only; it is not a production Supabase deployment or authenticated production authorization system.

- `record_context_source_revision` checks an active ProjectResource scope grant before reading Work/resource requirements, then records the observed commit SHA, tree SHA, source content hash, provenance and monotonic source version in the append-only Evidence Ledger plus a replaceable current-head pointer.
- `compile_context_pack` checks the scope grant before building a snapshot. Packs bind project, Work, physical repository/ref, Work version, dependency graph/target versions and states, ProjectResource grant version, decision IDs/versions/status/provenance, source commit/tree/content hashes, evidence refs and payload hashes, compiler/indexer/config versions and an explicit budget.
- Cache identity is derived from the complete snapshot fingerprint plus compiler, indexer, config and budget versions. `get_context_pack` rechecks current scope authorization and rebuilds the snapshot before selecting cached payload bytes; source/dependency/decision/grant/compiler/indexer/config/budget changes return `stale` with no old payload. Grant revocation returns `denied`.
- Lock ordering: Context compile/fetch acquire a shared Resource advisory lock, then a shared Project advisory lock, before authorization and retain both through snapshot/cache use. Resource, ProjectResource and resource-scoped OwnerDecision writers acquire exclusive Resource lock(s) in sorted UUID order before deriving and locking all associated Project IDs in sorted order. Authorization and snapshot reads use MVCC SELECTs without tuple locks, so readers do not wait on tuples held by BEFORE ROW writers. WorkResourceRequirement keeps the Stage 2A Work tuple lock first, then locks all affected Resource IDs in sorted order and then the Project lock; its validation uses MVCC for Resource state. `record_context_source_revision` obtains a shared Resource lock then an exclusive Project lock before its source-head `FOR UPDATE`. The two-session tests force decision-revocation/new-association and Resource-archive/new-association races, and require no authorization after the revoke/archive commits.

- Evidence preselection uses an append-only indexed metadata table. It counts serialized JSON UTF-8 bytes for `evidence_type`, `source_ref`, and `source_revision` as well as payload/provenance, bounds each variable field, caps candidate count at 128 and aggregate selected materialized bytes at 256 KiB including fixed per-row overhead, and joins full Evidence payload only after metadata selection. The summary distinguishes preselected rows/bytes from the final Pack's included rows after the later token-budget pass.
- Packs are immutable disposable projections. Source Evidence remains authoritative. Cross-project dependencies fail closed because this compiler slice does not yet implement explicit cross-project context grants. Evidence inclusion is deterministic and bounded using a documented UTF-8-bytes/4 token estimate rather than a model-specific tokenizer.
- Dependency batch mutation: the public `mutate_dependencies` wrapper locks the graph and idempotency receipt, locks the complete set of affected Work rows in sorted Work-ID order, then locks the full set of involved Projects in sorted project-ID order before calling the original atomic edge-mutation implementation. The renamed inner function is private to `aep_owner`; only the wrapper is executable by `aep_runtime`. This prevents two shared-graph batches with different edge orders from retaining project locks in conflicting orders.
- Scope: trusted single-Owner disposable PostgreSQL 17.12 prototype only. ProjectResource is not authenticated caller/session identity; the GitHub source observation is supplied by the calling adapter and is not independently authenticated by the database. This is not a production Supabase migration, authenticated multi-tenant authorization layer, GitHub retrieval service, or production indexer. T17/T18 remain PARTIAL.
